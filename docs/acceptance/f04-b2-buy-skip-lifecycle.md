# Ф-04 / B2. Окончательный пропуск BUY

В [задаче #38](https://github.com/prmAim/orbita/issues/38) проверяется судьба
10 лотов после подтверждённого брокером отказа. Исходная попытка сохраняет
статус брокера. Увеличение цели по тому же исходному ордеру с 10 до 12 даёт
право рассмотреть только два новых лота с обычными проверками отправки.
[Спецификация Ф-04, §§4, 6–7](../specifications/f04-r52-rejection-classification.md).

## Что проверяет B2

Стенд принимает реальные RPC Java SDK 1.51 на локальном TLS-сервере.
Приложение получает исходное исполнение через поток SDK, выставляет лимитную
заявку и сохраняет ответы по счёту повторения в PostgreSQL 17.11. На стороне
имитатора ведётся отдельный журнал RPC. Каждый сценарий получает свежую БД.
Для перезапуска B03 тест закрывает контекст Spring и создаёт новый над той же
БД и тем же имитатором. Первое и новое исполнения поступают по TLS, повтор
сохранённого исполнения передаётся синхронно в `CopyService.accept`, чтобы
проверить результат его обработки до следующей отправки.

| Критерий | Воздействие | Наблюдаемый результат |
| --- | --- | --- |
| B01 | BUY на 10 лотов, stream с причиной 2 и отдельный `GetOrderState` по UUID запроса. Параметры `REJECTED` и `CANCELLED` | Типизированная причина хранит `INSUFFICIENT_RESOURCES` и исходный terminal. Один `PostOrder` на 10, исполнено 0, окончательно пропущено 10, одно итоговое уведомление. |
| B03 | Доступные деньги по SDK растут с 10 000 до 20 000 RUB, встречная котировка со 100 до 105. Перезапуск, повтор прежнего исполнения, затем ещё 2 лота по тому же исходному ордеру | Старые 10 сохраняются как пропуск. После сверки и нового явного допуска журнал RPC содержит объёмы 10 и 2. У новой заявки 2 исполненных лота, у прежней 0. Обе встречные цены сохранены в БД. |
| B04 | Сначала unary фиксирует окончательный `OTHER`. Затем дважды приходит stream с причиной 2 | В истории остаётся исходный ответ, появляется одно уточнение причины, число отправок и итоговых уведомлений равно одному. |
| B05 | Разовый допуск израсходован. Отдельные варианты задают ручную паузу и паузу из-за расхождения позиции. Сначала в ответе отсутствует комиссия, затем имитатор передаёт явное нулевое значение | При квалифицированном `CANCELLED` основной резерв освобождён. В БД комиссия остаётся `null`, удерживаются 2 RUB на комиссию и дополнительный резерв. Независимая сверка подтверждает ноль и освобождает остаток. У попытки остаётся UUID использованного допуска, инструмент сохраняет паузу. |

Все четыре строки проходят через
[`BuyResourceRejectionWholeChainIT`](../../backend/src/test/java/ru/orbita/copy/BuyResourceRejectionWholeChainIT.java).
Доменная проверка отдельного приращения по исходному ордеру находится в
[`CopyCalculationTest`](../../backend/src/test/java/ru/orbita/copy/CopyCalculationTest.java).

## Локальная проверка

На первой версии сквозных тестов (база `3ebb8ff`, `dirty=true`) исполнитель подтвердил 211
проверок: 3 контракта фикстур, 108 unit/SDK/TLS и 100 PostgreSQL IT.
Failures/errors/skips — 0/0/0. Результат сохранён в
`.scratch/target-checks/run-tw7k02h1/summary.json`.

При подготовке стенда обнаружились две причины сбоев фикстуры. Открытие
подписки до сохранения границы наблюдения инвалидировало сверку. Очистка
таблиц между тестами через `TRUNCATE … CASCADE` удаляла начальную запись
`broker_connectivity`. Отдельное падение assertion относилось к ожидаемой
комиссии: имитатор явно сообщал 0 RUB после нулевого исполнения.
Эти результаты относятся к настройке стенда и тестовым ожиданиям.

## Независимое ревью

Код и исправления подготовила GPT-6 Luna / Max. Ревью провели два независимых
исполнителя GPT-6.2 Astra / High по направлениям Standards и Spec.

- В B03 повтор исходного исполнения теперь завершается до проверки числа
  отправок. Остаток проверяется отдельным чтением SDK, а встречная цена —
  по сохранённым данным каждой заявки.
- В B04 проверяется номер первоначальной записи `OTHER`, её содержимое после
  дублей и ссылка из записи квалификации. В B05 квалификация и пропуск 10 лотов
  проверяются непосредственно при неизвестной комиссии.
- Каждая параметризация начинает с чистой PostgreSQL. В B05 штатная сверка
  позиций выполняется как при отсутствующей комиссии, так и после её независимого
  подтверждения. В первом случае разовый допуск заблокирован. Во втором завершена
  сверка прежней попытки, а выдача следующего допуска остаётся явным действием.

На коде `c264885` оба ревьюера подтвердили закрытие замечаний. Standards — 0
открытых, Spec — 0 открытых. Ревью было статическим.
