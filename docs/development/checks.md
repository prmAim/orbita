# Проверки перед сборкой

Из корня репозитория используйте установленный Python 3.10+ (в готовом
окружении — `uv run --offline --no-sync python`). Эти две команды используют
только стандартную библиотеку; установка Python-пакетов не требуется.

## Совместимость временного набора

```powershell
python tools/check_demo_schema.py
```

Проверка читает миграции Flyway, явные квалификации в
`deploy/demo/schema-compatibility.json` и реальные защитные условия в Java
`InterfaceDemoLedger`, PowerShell Generate и SQL Remove. Текущая схема должна
быть явно квалифицирована для Generate и Remove; сохраняются старые пары
manifest 1/schema 15 и manifest 2/schema 16,17,18. Новая миграция сама по себе
не подтверждает совместимость: проверка завершится с ненулевым кодом до
сборок CI. При намеренном изменении guards обновите проверку и её регрессии.

До добавления новой квалификации проверьте Generate и Remove на отдельной
синтетической БД, включая принадлежность данных, сохранение пользовательских
записей и удаление старых наборов. Затем согласованно обновите квалификации,
защитные условия и доказательства. Проверка исходников не заменяет эту
квалификацию и не выполняет Generate/Remove или подключения к БД.

## Окружение Java

```powershell
python tools/check_dev_environment.py --java-home "<каталог JDK 25>" --maven-repository "<локальный Maven repository>" --build-directory "<отдельный каталог сборки>"
```

`--help` описывает параметры. `--java-home` имеет приоритет над `JAVA_HOME`,
затем выбирается `java` из PATH. Проверяются версия из POM и наличие `javac`.
Для зависшего launcher/shim действует отдельный таймаут каждого процесса
(`--timeout`, по умолчанию 5 секунд). CLI Docker можно выбрать через `--docker`.
Таймаут завершает только дерево запущенной диагностики: отдельную process
session на POSIX или частный Windows Job Object с kill-on-close. Windows
helper ждёт разрешения через stdin до запуска инструмента; при отказе
назначения job инструмент не запускается. Docker Engine не входит в это
дерево. Отказ создания/назначения job — ошибка диагностики, без изменения
прав доступа. Механизм описан в [документации Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

`--maven-user-home` (по умолчанию `MAVEN_USER_HOME` или `~/.m2`) выбирает
кэш дистрибутива Wrapper; `--maven-repository` выбирает кэш зависимостей.
Это разные каталоги. Без явного repository используется
`<maven-user-home>/repository`. Настройки `settings.xml`, `MAVEN_ARGS` и
полнота кэша зависимостей не проверяются. Выбор repository передаётся в
напечатанную команду явно. `--build-directory` по умолчанию `backend/target`;
для параллельных сборок укажите отдельный абсолютный путь.

Команда сообщает выбранные пути, JDK, версию Wrapper, наличие дистрибутива
именно из его URL и доступность Docker Engine через `docker version`.
Отдельно обозначаются `MISSING`, `ACCESS_DENIED`, `ENGINE_UNAVAILABLE`,
`TIMEOUT` и несовместимая версия. Ошибка даёт ненулевой код; исходный вывод
ошибок инструментов скрыт, чтобы не раскрывать локальные секреты.

Диагностика не запускает Maven Wrapper или Maven, не скачивает дистрибутив,
не создаёт каталогов, не устанавливает инструменты и не управляет Docker.
При успехе печатает готовую команду `spotless:check verify` для PowerShell
на Windows или POSIX shell на Linux, используя найденный кэшированный Maven
и `--offline`. Запустите её отдельно после сборки frontend по README.
При неполном кэше Maven завершится ошибкой без сетевой загрузки; наполнение
кэша — отдельная операция владельца. Успех диагностики не означает успешной
сборки, интеграционных тестов или живой приёмки.

Машинные пути передаются параметрами и не сохраняются в отслеживаемых
файлах. Локальные команды и журналы можно хранить в игнорируемом
`.scratch/dev-preflight/`. Пароли и токены в параметры не передавайте.

## Проверка самих инструментов

```powershell
uv run --offline --no-sync python -m unittest discover -s tests -p test_dev_checks.py -v
uv run --offline --no-sync ruff check src tests tools
uv run --offline --no-sync ruff format --check src tests tools
```

Тесты запускают настоящие CLI с временной копией guards и имитаторами JDK,
Maven и Docker; работающие службы им не нужны. В ограниченном Windows
окружении при запрете записи во временный каталог задайте `TEMP` и `TMP`
в доступный игнорируемый каталог перед запуском тестов. CI выполняет
проверку схемы сразу после checkout на системном Python 3.10+ Ubuntu runner,
до установки зависимостей frontend/backend; unittest входит в штатный
Python workflow. Живая приёмка выполняется отдельно по разрешению владельца.

## Целевые Java-проверки

Сначала проверьте схему и соберите frontend по README. Исполнитель сам
использует результат диагностики JDK и кэша Maven. Для наборов с IT он также
проверяет доступ к Docker Engine в том процессе, который затем запускает Maven.

```powershell
python tools/run_target_checks.py --suite b1 --java-home "<JDK 25>" --maven-user-home "<Maven user home>" --maven-repository "<repository>"
python tools/run_target_checks.py --fixture OrderEvidenceFixturesTest
python tools/run_target_checks.py --unit BuyResourceRejectionClassifierTest --it OrderEvidenceRestartIT
```

Укажите установленные пути, если значения окружения или пути по умолчанию
не подходят. `--fixture`, `--unit` и `--it` принимают точные имена классов,
их можно повторять. Набор `b1` сначала проверяет базовые фикстуры, затем
выполняет пять unit/SDK/TLS-классов и два PostgreSQL IT. Ошибка первого этапа
останавливает запуск. При выборе только unit-тестов Docker не требуется.

Каждый запуск создаёт каталог `.scratch/target-checks/run-*/`. Внутри находятся
`preflight.log`, журнал Maven и отдельный каталог сборки каждого этапа.
`--build-directory` у исполнителя меняет родительский каталог этих запусков.
В `summary.json` сохранены Git SHA и признак грязного дерева, выбранные классы,
аргументы Maven, его exit code, имена фактически выполненных тестов по классам
из XML Surefire и Failsafe, число выполненных тестов, failures/errors/skipped
и итог исполнителя.
Выполненные тесты считаются без skipped. Для успеха каждый запрошенный класс
должен дать хотя бы один выполненный тест, а все этапы — пройти без ошибок.
Пропуск одного класса обнаруживается и при успешном выполнении соседних.
Для разбора метода поле `report` указывает на его XML. При `dirty=true` SHA
описывает базовый коммит, локальные изменения также входят в проверку.

| Итог | Что проверить |
| --- | --- |
| `ENVIRONMENT` | Открыть preflight или Maven log, сверить JDK, offline-кэш и доступ текущего процесса к Docker. |
| `COMPILATION` | Открыть сообщение компилятора, в том числе для testCompile. |
| `FIXTURE_FAILURE` | Падает отдельно запущенный контракт базовых данных. Исправить фикстуру или её assertion до PostgreSQL-прогона. |
| `TEST_FAILURE_REVIEW` | Прочитать исключение и конкретный assertion. Зафиксировать поведенческий RED только после сверки фактического состояния заявки и типизированной записи с ожидаемыми. Ошибку assertion, setup или контейнера указать по первопричине. |
| `TARGETS_NOT_EXECUTED` / `REPORT_ERROR` | Проверить выбор классов, skip-параметры и XML этого запуска. |
| `MAVEN_FAILURE` | Прочитать ошибку цели в журнале, например сообщение об отсутствии указанного теста. |

При передаче исполнителю укажите путь к игнорируемому `summary.json`.
Он содержит выбранные пути, версию Engine при успешной проверке, имя Docker
context и признак переопределения Docker host. Параметр `--access-context`
помечает фактический запуск (`shell`, `sandbox` или `approved`).
Следующий исполнитель повторяет диагностику под своей учётной записью.
Локальное разрешение на доступ к Docker действует в контексте запуска.

## GitHub CI и ожидание результата

Оба workflow запускаются для PR и push в `main`. Новая проверка отменяет
устаревший запуск того же PR: группа конкуренции задана на уровне workflow,
до вычисления области проверок. Для каждого push в `main` используется
собственная группа по ID запуска, и эти проверки не отменяют друг друга.
Поэтому лёгкая публикация отчёта или более поздний commit не отменит полный
набор для другого SHA. У PR и push раздельная история. Задания `verify` и
`checks` запускаются также для отчётов. Лёгкий режим проверяет заголовки и
локальные файловые ссылки отчётов, пробельные ошибки diff и совместимость
схемы. Он применяется только к изменениям `docs/acceptance/*.md`. Смешанный
diff, изменения спецификации, инструментов, схемы, workflow и неизвестная
база запускают полный набор.
Для PR сравнивается вся ветка от merge base, для push — обе границы события.
Переименование учитывает старый и новый путь.

Для проверки защиты ветки используйте `gh api repos/prmAim/orbita/branches/main`
и `gh api repos/prmAim/orbita/rules/branches/main`. На 18.11.2026 обязательные
контексты и применимые rulesets для `main` отсутствовали. Имена workflow и jobs
сохранены. Выбор режима внутри job позволяет завершить статус и для PR,
содержащего только отчёты.

```powershell
python tools/watch_ci.py <полный-SHA-головы-PR> --event pull_request
python tools/watch_ci.py <полный-SHA-в-main> --event push
```

Один процесс наблюдает оба workflow для выбранных SHA и события. Для push
по умолчанию выбрана ветка main. При нескольких совпадениях укажите
`--branch`. Наблюдатель выводит смену этапа и итог со ссылкой, возвращает
ненулевой код при ошибке, отмене или истечении времени. Период опроса по
умолчанию 60 секунд, предел ожидания 40 минут. В чат передавайте смену
существенного этапа, ошибку и завершение.
