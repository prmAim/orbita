# Ревью решений по брокерским событиям

Для каждого изменённого правила проследите одно событие от сырого ответа до
проверки полей, сохранённого receipt, решения по заявке и replay в новом
контексте приложения на той же PostgreSQL. Укажите метод теста или параметр
для каждой применимой ячейки. Если сочетание невозможно, запишите причину.
Полноту проверяет reviewer, в том числе по событиям, которые пришли, но ещё
не применены. Число зелёных тестов само по себе этого не устанавливает.

## Матрица B1

| Что меняет один вход | До квалификации | После квалификации | После перезапуска | После следующего корректного ответа |
| --- | --- | --- | --- | --- |
| Исполнение без UUID, но счёт и оба ID совпадают с доказанной связью | Сохранить receipt, учесть исполнение после привязки, исключить нулевую причину | Отозвать причину, учесть исполнение один раз | Восстановить связь и количество из журнала | Нулевой ответ не стирает исполнение |
| Статус и объёмы противоречат друг другу, например NEW с отменённым лотом | Сохранить противоречие, не квалифицировать | Отозвать причину | Повторить решение с полной историей | Корректная сумма нового кадра не устраняет старое противоречие |
| Размер лота потока расходится с независимым справочником | Сохранить расхождение, не квалифицировать | Отозвать причину и запросить сверку | Учесть receipt, сохранённый до сбоя транзакции решения | Корректные stream и unary не возвращают квалификацию |
| Исполнение из `TradesStream` с тем же счётом и биржевым ID | Не квалифицировать нулевую причину; учесть исполнение | Отозвать причину с `OTHER`, сохранить исполнение | Восстановить исполнение или отзыв из журнала | Следующий корректный unary не стирает исполнение и не снимает отзыв |
| Справочник недоступен при известном конечном unary | Зафиксировать исход без специальной причины | Сохранить исход, отозвать неподтверждённую причину | Применить сохранённый unary и при недоступном справочнике | После восстановления проверить полный предикат заново |

Штатный ход для сравнения — одна исходная BUY-попытка, terminal stream и
независимый GetOrderState. Проверьте происхождение каждого значения. Для unary
счёт берётся из запроса, биржевой ID сверяется со stream trade-order ID.
Отдельно проследите чужой счёт, совпадение только одного ID и ответ собственной
отмены. Для размера лота задавайте значение в событии независимо от симулятора
справочника. Сохранённая ошибка в истории и временный отказ чтения имеют
разные последствия при следующем ответе.

## Доказательства

- Начните с согласованной пары из `OrderEvidenceFixtures`. Её контракт проверяет
  `OrderEvidenceFixturesTest` без Spring и PostgreSQL. В отрицательной фикстуре
  передайте противоречащее значение явно, сохранив остальные условия.
- `OrderEvidenceIT` проверяет первоначальное решение, поздний отзыв и контроль
  чужих событий. `trade` в `OrderEvidenceRestartIT` использует фактический
  источник `TRADES_STREAM`; `uuid-less` проверяет отдельный поток состояний без
  UUID. В `OrderEvidenceRestartIT` используйте пары `uuid-less`, `volume`,
  `lot-size`, `metadata`, `trade`. Параметр `late=false` вводит событие до
  квалификации, `late=true` — после неё. Проверьте состояние после replay и
  сразу после следующего корректного unary по отдельности.
- Для проверки причины читайте последнюю `ReasonEvidence` по UUID заявки.
  Различайте пустую историю и последнюю запись отзыва с причиной `OTHER`.
  Сверьте статус заявки, исполненные и пропущенные лоты, число отправок и
  уведомлений. Текст причины проверяйте в сценариях отображения.
- Укажите, откуда взялся ожидаемый результат, какое единственное условие
  нарушено и на каком assertion получен RED. Сбой настройки, фикстуры или
  проверки nullable-поля отмечайте отдельно от ошибки поведения.
