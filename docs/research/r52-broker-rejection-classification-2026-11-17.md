# Ф-04 / R52: квалификация отказов T-Invest API

Дата исследования: **2026-11-17**. База Orbita: `344985a88c597a443247feb6690d967a78313feb`; зависимость `ru.tinkoff.piapi:java-sdk-core:1.51`. Статус: исследование и рекомендации, не согласованная реализация и не закрытие Ф-04.

## Вывод

**Публичных контрактов недостаточно для полного достоверного подключения `HALTED` и отдельных production-причин «нет денег BUY» / «нет бумаг SELL».** Не найден типизированный признак остановки торгов конкретной заявки, одновременно подтверждающий окончательный отказ без исполнения. Ошибка `30098` — кандидат для дополнительной квалификации, но не достаточное основание разрешить повтор R52. Код ошибки RPC, состояние заявки и причина отказа — разные факты. [Каталог ошибок][errors], [контракт SDK 1.51][contract151].

Найден полезный типизированный ресурсный сигнал: `OrderStateStreamResponse.StatusCauseInfo.CAUSE_CANCELLED_NOT_ENOUGH_POSITION = 2`. Официальное описание: «Заявка не выставлена из-за нехватки средств». Он есть **уже в SDK 1.51**, но только в `status_info` потока состояний; это не поле unary `GetOrderState`. Контракт не выделяет отдельно деньги покупки и бумаги продажи, не перечисляет допустимые сочетания причины со статусами и не гарантирует доставку причины после восстановления соединения. Для BUY это основание исследовать ограниченное сопоставление с `INSUFFICIENT_RESOURCES` при подтверждённых идентичности, окончательности и нулевом исполнении. Для SELL смысл «нехватки средств» как именно нехватки собственных бумаг требует уточнения у владельца API. [Текущая справка методов][methods], [опубликованный контракт 1.51][contract151].

Отсутствие квалифицированной причины **не отменяет** достоверно установленный конечный статус: подтверждённый `REJECTED`/`CANCELLED` с неизвестной причиной остаётся известным результатом с `OTHER`. `UNKNOWN` нужен, когда неизвестны сам исход, идентичность, объём или окончательность. Ни один из этих случаев сам по себе не разрешает специальный повтор. Это рекомендация в рамках [R41/R52/R125, issue #10][spec], а не новое правило API.

## Что действительно приходит через SDK 1.51

**Код, unary.** `PostOrderResponse` содержит `execution_report_status`, `lots_requested`, `lots_executed`, `order_id`, `order_request_id`, `message`, комиссии и идентичность инструмента/направления. Поле `message` — строка дополнительных сведений, не enum причины. Unary `OrderState` содержит статус, объёмы, `stages`, комиссии и идентификаторы, но **не содержит** `message` или `status_info`. Оба типа не имеют типизированного `HALTED` или отдельного reason-code ресурсов. Проверены generated-классы `ru/tinkoff/piapi/contract/v1/{PostOrderResponse,OrderState}.java`. [Source-JAR 1.51][contract151].

**Код, stream.** `OrderStateStreamResponse.OrderState` содержит optional `status_info`, optional `order_request_id`, `account_id`, направление, инструмент, `lots_requested/executed/left/cancelled`, `trades`, `trade_order_id`. `hasStatusInfo()` отличает отсутствие причины; неизвестное enum-значение нужно сохранять как неизвестное, не превращать в разрешение повтора. Кроме ресурсного значения 2 перечислены только `CAUSE_UNSPECIFIED=0`, `CAUSE_CANCELLED_BY_EXCHANGE=1`, `CAUSE_CANCELLED_BY_CLIENT_BLOCK=3`, `CAUSE_REJECTED_BY_BROKER=4`, `CAUSE_REJECTED_BY_EXCHANGE=5`, `CAUSE_CANCELLED_BY_BROKER=6`, `CAUSE_CANCELLED_BY_CLIENT=15`. Ни одно generic broker/exchange значение не доказывает остановку. [Source-JAR 1.51, `OrderStateStreamResponse.java`][contract151].

**Контракт потока.** Первое `order_id` может быть внутренним номером до появления биржевого. Клиентский UID в `order_request_id` пригоден для связи с запросом; не-UID может быть заменён сервером. Список `trades` может отсутствовать, поэтому пустой список не доказывает отсутствие сделок. Кроме того, после частичного исполнения отменённая заявка в потоке остаётся `PARTIALLY_FILL`, а не становится `CANCELLED`. Рекомендация: окончательность частично исполненной заявки подтверждать сверкой, сопоставляя итоговые объёмы; не переносить unary-автомат состояний на stream. [Текущая документация потока][stream].

**Код, ошибки RPC.** `ru/ttech/piapi/core/connector/SyncStubWrapper.callSyncMethod` оборачивает `Throwable` в `ServiceRuntimeException`; успешный protobuf-ответ `REJECTED` не является исключением. В `ServiceRuntimeException.java`:

| Java API | Откуда берётся значение | Ограничение |
|---|---|---|
| `getErrorType()` | `Status.fromThrowable(...).getCode()` | Это gRPC-категория, не причина R52 |
| `getErrorCode()` | `Status.getDescription()` | Строка, обычно ожидается брокерский числовой код; нельзя читать её как текст причины или integer без проверки |
| `parseErrorCode()` | `Integer.parseInt(getErrorCode())` | При null/нечисловом значении возвращает **0**, а не подтверждённый брокерский код |
| `getDescription()` | ASCII trailer `message` | При отсутствии — `Unknown error`; не структурированный enum |
| `getTrackingId()` | ASCII trailer `x-tracking-id` | Диагностическая корреляция RPC, не UUID заявки |
| `getMetadata()` | `StatusRuntimeException.getTrailers()` | Только когда непосредственное исключение — `StatusRuntimeException`; вложенная обёртка может сохранить status через cause, но потерять извлечение trailers |

Это наблюдения **именно source-JAR 1.51**, не гарантия того, какие trailers вернёт каждый серверный путь. SDK не извлекает initial response headers этим методом. Документация брокера подтверждает назначение `message` и `x-tracking-id`, но не обещает постоянный формат свободного текста. Поэтому нельзя классифицировать по `Throwable.getMessage()`, подстрокам «денег»/«торги» или одному `INVALID_ARGUMENT`. Диагностика должна сохранять отдельно status, исходный error-code, безопасные message/tracking-id и UUID попытки; `toString()` исключения печатает metadata целиком и не подходит для безусловного журналирования. [Core 1.51][core151], [metadata API][metadata].

`newSyncService` создаёт обычный `SyncStubWrapper`; resilience-обёртка имеет отдельную фабрику. Это объясняет, почему текущий адаптер использует обычный путь для мутаций. Наличие такой обёртки не является доказательством отсутствия всех повторов на транспортном уровне: число обработанных `PostOrder` должен проверять изолированный TLS-сервер. [Core 1.51, `ServiceStubFactory.java`][core151], [локальный post, строка 96](../../backend/src/main/java/ru/orbita/broker/TInvestBrokerGateway.java#L96).

## Матрица первичных сигналов

Во всех строках «известный» предполагает проверку связи с конкретной попыткой: счёт, UUID запроса, инструмент, направление, объёмы и отсутствие противоречащих уже сохранённых исполнений. Это рекомендуемый барьер Orbita.

| Первичный сигнал | Что подтверждено / чего не хватает | SDK 1.51 | Допустимый результат и действие |
|---|---|---|---|
| Unary `REJECTED`, согласованные нулевые исполнения | Конечный отказ; квалифицированная причина не сообщена | PostOrder и GetOrderState | Известный `REJECTED/OTHER`; окончательный пропуск по действующему правилу, без специального повтора |
| Unary `CANCELLED`, согласованные исполнения | Отмена остатка; не обязательно отказ при размещении и не обязательно ноль | GetOrderState | Известная отмена; учесть все сделки, окончательно обработать остаток. Не переименовывать автоматически в `REJECTED` |
| Связанный terminal-zero-fill + stream `status_info=2` | Типизированная нехватка средств; BUY/SELL-разделение и покрытие причин не специфицированы | Есть в OrderStateStream | Рекомендуемый кандидат BUY `INSUFFICIENT_RESOURCES` после квалификации сочетания статусов; SELL требует подтверждения смысла. Никакого уменьшенного PostOrder |
| `status_info=2`, но NEW/неизвестная окончательность или противоречащие fills | Причина не заменяет доказательство финального исхода | Есть | Сверка; не создавать вымышленный нулевой отказ |
| Generic stream reject/cancel cause, terminal подтверждён | Кто отклонил/отменил; не почему | Есть | `OTHER` при известном исходе; причина не даёт `HALTED` |
| RPC `30098`, даже вместе с текущим закрытым trading status | Семантика RPC-кода; нет гарантии конечного отказа конкретной заявки без fills | ServiceRuntimeException | Не включать `HALTED` автоматически; получить исход сверкой. При подтверждённом terminal — `OTHER` до квалификации причины |
| Свободный `message`, похожий на resource/halt | Нестабильная строка без перечня допустимых значений | PostOrder либо trailers | Диагностика; не разрешение повтора |
| `DEADLINE_EXCEEDED`, `UNAVAILABLE`, `INTERNAL`, потерянный ответ | Возможен принятый/исполненный запрос | SDK exception | `UNKNOWN`, сохранить резерв и блокировку, читать тот же UUID; не PostOrder |
| `RESOURCE_EXHAUSTED` без квалифицированного terminal | Транспортная/сервисная категория, не средства счёта | SDK exception | Не `INSUFFICIENT_RESOURCES`; сверка исхода мутации |
| `GetOrderState` not-found, пустой GetOrders, молчащий/оборванный stream | Нет наблюдения заявки; отсутствие заявки не доказано | Есть | Исход остаётся `UNKNOWN`, пока нет независимого подтверждения |
| FILL / PARTIALLYFILL или любая подтверждённая сделка | Нулевое исполнение опровергнуто | Unary/stages/TradesStream | Учёт фактического исполнения; при отмене сверка остатка, без R52-повтора всего объёма |

Основания полей и статусов: [контракт 1.51][contract151], [stream][stream]. `DEADLINE_EXCEEDED` по gRPC может прийти после успешного изменения состояния; `UNAVAILABLE` не делает повтор неидемпотентного действия безопасным; `RESOURCE_EXHAUSTED` имеет общий ресурсный/квотный смысл. Это прямое ограничение интерпретации транспортных ошибок. [gRPC status codes][grpc].

Снимок `GetTradingStatus`, расписание, текущие деньги или бумаги полезны для **новой** проверки возможности операции. Они не привязаны к причине отказа конкретного UUID, а время между запросами допускает изменение состояния. Вывод «было закрыто, значит эта заявка точно отклонена из-за остановки» не следует из опубликованного контракта. Это логический вывод об ограничении источников, согласованный с [полями API][methods] и [правилами доступности](https://github.com/RussianInvestments/investAPI/blob/3eaf23a25f598fe483c913184acdbd9132bc68d2/src/docs/orders_details.md).

## Идентичность, частичное исполнение и сверка

`PostOrderRequest.order_id` — клиентский UID идемпотентности; `PostOrderResponse.order_id` — брокерский/биржевой номер. Их нельзя смешивать с `x-tracking-id`. В `GetOrderStateRequest` SDK 1.51 поддерживает `order_id_type=ORDER_ID_TYPE_REQUEST`, поэтому после утраты ответа можно читать сохранённый UID вместе со счётом; при известном биржевом идентификаторе использовать соответствующий тип. Поток возвращает `order_request_id`, а также отдельный `trade_order_id`; каждый идентификатор должен сохранять своё назначение. [Контракт 1.51][contract151], [metadata][metadata].

В официальных исторических материалах есть расхождения: [FAQ](https://github.com/RussianInvestments/investAPI/blob/3eaf23a25f598fe483c913184acdbd9132bc68d2/src/docs/faq_orders.md) описывает повтор как возврат состояния, [head-orders](https://github.com/RussianInvestments/investAPI/blob/3eaf23a25f598fe483c913184acdbd9132bc68d2/src/docs/head-orders.md) — как `30057`. FAQ также содержит устаревшее утверждение об отсутствии ключа в других сущностях и оговорку о негарантированной сохранности месячного ключа. Эти тексты не дают права предполагать бессрочную дедупликацию, считать not-found доказательством отсутствия сделки или повторять PostOrder вместо чтения. Для полей приоритет имеет проверенный контракт 1.51; для Orbita запрет слепого повтора уже установлен R41. Это документированное расхождение источников, оставляемое для уточнения, а не выбранная нами новая семантика сервера.

`CancelOrderResponse` сообщает время отмены и metadata, но не окончательный исполненный объём. После отмены нужна сверка: сделка могла пройти до обработки отмены. `OrderStage.quantity` в 1.51 измеряется лотами, `OrderTrade.quantity` — штуками. Суммы и уникальные `trade_id` нужно сопоставлять с `lots_executed`, лотностью и уже записанными сделками; пустой optional список не является нулём. При расхождении старое доказанное исполнение не уменьшается. Последнее — рекомендация, согласованная с архитектурой Orbita. [Контракт 1.51: `CancelOrderResponse`, `OrderStageOrBuilder`, `OrderTradeOrBuilder`][contract151], [архитектура](../architecture/application.md).

## Рекомендуемый консервативный порядок решения

1. Сохранить неизменяемую идентичность попытки и доказательства до интерпретации. Не смешивать новый ответ RPC с причиной другой заявки или старой попытки.
2. Сначала определить **исход**: известный active/partial/terminal либо `UNKNOWN`. Проверить статус, идентичность, согласованность объёмов и ранее наблюдавшихся сделок. Exception/тайм-аут не подменять отказом.
3. Отдельно определить **причину**, только из квалифицированного для этого метода/контура/версии признака. Неизвестная причина при известном terminal — `OTHER`; недоказанный terminal — `UNKNOWN`.
4. Существующее исполнение исключает ветку «отказ без исполнения». Подтвердить отмену остатка и учесть сделки, пришедшие при отмене; не повторять полный первоначальный объём.
5. При доказанном ресурсном отказе без исполнения окончательно пропустить объём с причиной, без уменьшенной заявки. Сохранить исходные broker status/cause: не превращать каждую ресурсную `CANCELLED` в `REJECTED` ради имеющегося интерфейса.
6. До получения недостающего контракта `HALTED` не выводить автоматически из `30098` или снимка рынка. Если позже основание будет квалифицировано, применять все существующие ограничения R52/R125 и исправленную окончательную проверку Ф-03.
7. При неопределённости оставить резерв и запрет новой заявки, выполнять сверку по прежней идентичности. Потеря stream-причины после рестарта не должна восстанавливаться догадкой. Установленный конечный результат не возвращать в UNKNOWN лишь из-за отсутствия причины.

Это предлагаемая схема для следующей спецификации, а не реализованное изменение.

Локальные ограничения реализации на указанном commit: [post, строки 96–147, и reconcile, строки 153–222](../../backend/src/main/java/ru/orbita/broker/TInvestBrokerGateway.java#L96) передают подтверждённый `REJECTED` как `OTHER`, runtime-ошибки — как `UNKNOWN`; [SourceExecutionFeed, строка 66](../../backend/src/main/java/ru/orbita/broker/SourceExecutionFeed.java#L66) использует TradesStream, не OrderStateStream. Подключение нового потока — отдельная инженерная задача с долговечным сохранением причин и восстановлением, не только `switch` по коду.

[TradingService, строка 635](../../backend/src/main/java/ru/orbita/copy/TradingService.java#L635) разрешает HALTED-путь только для `REJECTED + HALTED + executedLots=0`, вне acceptanceAttempt и при наличии исходной котировки. [commission, строка 248](../../backend/src/main/java/ru/orbita/broker/TInvestBrokerGateway.java#L248) читает GetOrderState. Поэтому ранний отказ без созданной заявки/биржевого номера требует отдельно определить подтверждение комиссии и освобождение резервов/разового допуска. Нельзя выдумывать brokerOrderId, нулевую комиссию или успешную независимую сверку, чтобы протолкнуть такой результат через текущую модель.

## План последующих изолированных проверок — NOT_RUN

Тесты ниже — предложения для `/to-spec → /to-tickets → /tdd`, не выполненная приёмка. Только unit и официальный SDK 1.51 против локального TLS-имитатора; без реальных счетов, токенов, брокера и Telegram. Имитатор проверяет проводку и решение Orbita, **не истинность поведения сервера брокера**.

| Группа | Сценарии и обязательные наблюдения |
|---|---|
| SDK exception mapping | Сервер возвращает status с числовой description и отдельными trailers message/tracking-id; проверить точное извлечение. Отдельно null/нечисловой код, отсутствующие trailers, обёрнутое исключение, неизвестный enum. Не заменять неизвестное кодом 0 как бизнес-причиной |
| Известный отказ / неизвестная причина | PostOrder и GetOrderState: REJECTED/zero-fill без причины → OTHER. CANCELLED с ненулевыми fills остаётся отменой с исполнениями. Новых PostOrder нет |
| Ресурсная причина BUY | Терминальный согласованный zero-fill + связанный stream cause=2 → после утверждения спецификации окончательный пропуск исходного объёма; последующее увеличение/уменьшение доступных средств не создаёт уменьшенную заявку |
| Ресурсная причина SELL | Аналогичное доказательство по бумагам — положительный тест только после подтверждения семантики API для SELL. До этого отрицательный тест: неоднозначный сигнал не объявляется квалифицированной нехваткой собственных бумаг |
| Отрицательная квалификация | 30034 production, 30042, margin/limits/quota-коды, generic reject/cancel, свободные тексты, закрытый status snapshot, `30098` без дополнительной гарантии: не дают HALTED или квалифицированного resource-reason |
| Неизвестный результат | Имитатор принимает заявку и теряет ответ; отдельные deadline/unavailable/internal. За все проходы и восстановление один обработанный PostOrder, чтение прежнего UUID с REQUEST, резерв остаётся до сверки; not-found и разрыв stream не разрешают новую отправку |
| Stream correlation | Другая учётная запись/UUID/сторона/инструмент, отсутствующий request-id, внутренний первый order-id, неизвестная причина; ни один сигнал не относится автоматически к намерению. Дубликаты и события до unary-ответа не удваивают fills; восстановление не выдумывает утраченную причину |
| Частичное исполнение / отмена | Частичный fill, отмена, поздняя сделка; stream остаётся PARTIALLY_FILL. Проверить итог unary/объёмы, units versus lots и уникальность trade-id; нулевой список trades не обнуляет исполнение; R52 полного повтора не запускается |
| HALTED | Сейчас положительный **контрактный** TLS-кейс заблокирован отсутствием квалифицированного реального признака. После подтверждения: zero-fill + точная причина, весь объём, BUY/SELL, равная/лучшая/худшая последняя котировка, возраст/R21–R23, запрет повторной первой живой попытки R125. Искусственный domain HALTED проверяет только политику, не закрывает Ф-04 |
| Ранний отказ без brokerOrderId | Причина/отсутствие заявки и комиссия проверяются независимо; отсутствие GetOrderState не превращается в нулевую комиссию. Проверить резерв и запрет нового разового допуска до необходимых подтверждений |

## Что требуется подтвердить у владельца API

1. Какой точный машинный признак для **этого PostOrder UUID** означает отказ из-за остановки торгов без исполнения? Гарантирует ли `30098` отсутствие размещения/исполнения, и отличает ли остановку от закрытой/неподходящей сессии? Может ли ошибка возникнуть при повторном UUID уже существующей заявки? Нужна семантика, а не только пример текста.
2. Каковы production-признаки отдельно для нехватки собственных денег BUY и собственных бумаг SELL? Охватывает ли `CAUSE_CANCELLED_NOT_ENOUGH_POSITION=2` обе стороны, комиссии, маржинальные ограничения? Какие `execution_report_status` с ним допустимы и означает ли он неизменно нулевое исполнение?
3. Гарантируется ли доставка resource/halt-причины для отказов до появления биржевого order-id? Можно ли прочитать её после reconnect/restart, если unary OrderState её не содержит? Каково окно хранения и способ доказательства отсутствия заявки при REQUEST lookup not-found?
4. Как подтвердить отсутствие комиссии и окончательное отсутствие заявки после раннего отказа, если GetOrderState недоступен? Как связать все внутренние/биржевые номера с клиентским UUID без эвристик?
5. Какие актуальные гарантии дедупликации и хранения ключа заменяют противоречащие старые FAQ/head-orders? Ответ не отменяет R41, но нужен для границ сверки.

**Блокер Ф-04:** без этих сведений нельзя честно объявить доказанными оба требуемых специальных пути. Уже сейчас можно специфицировать отрицательную квалификацию, сохранение доказательств и корректную неопределённость; положительный HALTED-кейс нельзя «доказать» самим придуманным ответом имитатора.
