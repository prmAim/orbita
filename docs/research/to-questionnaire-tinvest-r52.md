# Вопросы к Т‑Банку об отказе SELL и остановке торгов

Материалы обращения в поддержку T‑Invest API по Ф‑04. Orbita отправляет лимитные заявки через T-Invest Java SDK 1.51. Для решения о пропуске SELL или специальном повторе после остановки торгов нужны причина окончательного отказа и подтверждение нулевого исполнения по счёту и исходному UUID.

## Что уже установлено

- **Связь заявки с потоком.** В первом событии брокер передаёт внутренний `order_id`: биржевой номер появляется позже. Если в `PostOrder` передан корректный UUID, поток возвращает его в `order_request_id`. Это объясняет два разных `order_id` при одном UUID в нашем прогоне. При отмене остатка после частичного исполнения заявка в потоке сохраняет статус частичного исполнения. [Стрим заявок](https://developer.tbank.ru/invest/services/orders/orders_state_stream)
- **Подтверждение непокрытой позиции.** По FAQ флаг `confirm_margin_trade` применяется к клиентам с начальным уровнем риска (КНУР). Уровень доступен в `GetInfo.risk_level_code`. Если предварительная проверка выявила нехватку собственных средств, при `false` или отсутствии согласия заявка такого клиента отклоняется. Код `30240` означает необходимость подтверждения возможной непокрытой позиции. [FAQ торговых поручений](https://developer.tbank.ru/invest/services/orders/faq_orders/) · [Каталог ошибок](https://developer.tbank.ru/invest/intro/developer/error-codes/errors/)
- **Причина и восстановление связи.** В Java SDK 1.51 поле `status_info` есть в `OrderStateStream`. Значение `CAUSE_CANCELLED_NOT_ENOUGH_POSITION = 2` описано как нехватка средств. В ответе `GetOrderState` этого поля нет. Core восстанавливает подписку после разрыва при использовании resilience-обёртки. В описании обёртки нет гарантии повторной доставки пропущенного события. [Методы сервиса заявок](https://developer.tbank.ru/invest/services/orders/methods) · [Java SDK Core](https://developer.tbank.ru/invest/sdk/java_sdk/faq_java_core)
- **Доступность торгов.** Код `30098` сообщает, что по инструменту сейчас нет торгов. `GetTradingStatus` и подписка `Info` показывают режим инструмента, включая биржевой перерыв `BREAK_IN_TRADING`. В перечне методов песочницы команды для принудительной остановки мы не нашли. [Каталог ошибок](https://developer.tbank.ru/invest/intro/developer/error-codes/errors/) · [Торговые статусы](https://developer.tbank.ru/invest/intro/intro/faq_trading_status) · [Методы песочницы](https://developer.tbank.ru/invest/intro/developer/sandbox/methods)
- **Пример Strategy v1.51.** Бэктест использует архив свечей. Торговый пример запрашивает `GetMaxLots` и пропускает SELL, если доступно 0 лотов. В модуле и его примерах мы не нашли записанных ответов брокера на интересующие нас отказы. [Java SDK Strategy](https://developer.tbank.ru/invest/sdk/java_sdk/faq_java_strategy) · [TradingServiceExample v1.51](https://opensource.tbank.ru/invest/invest-java/-/blob/v1.51/example/basic-example/src/main/java/ru/ttech/piapi/example/strategy/live/TradingServiceExample.java)

**Наблюдение в песочнице, 18 ноября 2026 года.** При нормальных торгах на счёте было 10 000 ₽ и 0 акций SBER. Лимитный SELL на 1 лот с `confirm_margin_trade=false` исполнился, позиция стала −1 акция. Для одного UUID поток передал `NEW → NEW → FILL` без `status_info`, а `PostOrder` и три чтения `GetOrderState` вернули `FILL`. Уровень риска счёта в опыте не измеряли. Остановку торгов и отказ SELL не наблюдали. [Протокол по UUID](https://github.com/prmAim/orbita/issues/39#issuecomment-6977669393)

## Письменный ответ Т‑Банка, получен к 19 ноября 2026 года

1. Банк учитывает `confirm_margin_trade` только при начальном уровне риска клиента. При другом уровне, включённой маржинальной торговле и достаточном обеспечении заявка может пройти без предупреждения. Для проверки перед выставлением банк назвал `GetMaxLots`, `GetPositions` и `GetPortfolio`. Это согласуется с исполнением SELL в песочнице. Уровень риска того счёта неизвестен.
2. Ошибка `30098` возможна только при выставлении заявки. Статус заявки можно запросить через `GetOrderState`.
3. Для сверки по исходному UUID банк подтвердил `GetOrderState` с `ORDER_ID_TYPE_REQUEST`. Ответ касается статуса. Гарантию восстановления причины пропущенного события или наличия записи после раннего отказа банк не указал.
4. По вопросу о воспроизведении остановки торгов в песочнице банк сообщил, что такого инструмента нет. Способ воспроизвести отказ SELL из-за нехватки собственных бумаг в ответе также не указан.

## Отправленные уточнения

1. **SELL.** Какое поле и значение однозначно указывают, что конкретный SELL отклонён из-за нехватки собственных бумаг? Может ли `status_info=2` также означать нехватку обеспечения или блокировку бумаг? Как по тому же UUID отличить окончательный отказ с нулём исполненных лотов от отмены остатка после частичного исполнения и установить причину, если событие потока пропущено?
2. **HALTED.** Как по счёту и UUID отличить отказ из-за остановки торгов от обычного закрытия сессии и подтвердить окончательный исход с нулевым исполнением? Что гарантирует `30098`, если заявка с этим UUID уже была принята, и какой вывод допустим, если после ошибки `GetOrderState` по UUID возвращает «не найдено»?

## Ответ на два отправленных уточнения

Источник — письменные ответы поддержки, переданные владельцем проекта и зафиксированные
в [#39](https://github.com/prmAim/orbita/issues/39). В проекте проверялся контракт Java SDK 1.51.
Поддержка не указала версию серверного API и не разделила гарантии для промышленного
контура и песочницы. Наблюдение конкретной заявки выше относится только к песочнице.

- **SELL.** Для описанного отказа банк указал ошибку `30042` при выставлении заявки. Позднее получить причину через API нельзя. В каталоге этот код означает нехватку активов для маржинальной сделки. Ответ не устанавливает, что код уникален для нехватки собственных бумаг или что `status_info=2` заменяет причину из ответа на выставление. [Каталог ошибок Т‑Банка](https://developer.tbank.ru/invest/intro/developer/error-codes/errors/)
- **HALTED.** По `30098` нельзя отличить остановку торгов от штатно закрытой сессии. По оценке банка, «не найдено» при сверке по исходному UUID с очень высокой вероятностью означает, что заявка не выставлялась. При техническом сбое банк этого не гарантирует.
**Следствие для Ф‑04.** Одного `30042` недостаточно для автоматического пропуска SELL. Сочетание `30098` и «не найдено» не подтверждает нулевое исполнение и не разрешает специальный повтор. Пока исход неизвестен, действует R41 — сохранить резерв и сверять исходную заявку по счёту и UUID без повторной отправки.
