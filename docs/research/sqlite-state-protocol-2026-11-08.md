# SQLite для журнала повторения сделок: границы протокола

Дата проверки первичных источников: 2026-11-08. Контекст:
[«Проверить гарантии SQLite для журнала, сбоев и резервных копий»](https://github.com/prmAim/orbita/issues/12).
Документальное исследование; код, SQL, контейнеры, финансовые операции и испытания
хранилища не выполнялись. Ниже факты документации отделены от проектных рекомендаций.

## Вывод и область решения

**SQLite подходит как кандидат для одной программы повторения на одном хосте**,
с последующим переносом на один сервер, если журнал размещён на проверенном
локальном постоянном хранилище, используется WAL с синхронизацией FULL,
а отправкой заявок владеет единственный активный экземпляр программы.
Это инженерный вывод для заданной топологии, а не подтверждение готовности
конкретной установки. Скорость фиксации и восстановление ещё требуют испытаний.

Транзакция базы не включает брокера. Поэтому даже исправная база не доказывает,
что заявка не была исполнена после потери ответа. Проектный протокол должен
сохранять намерение до внешнего действия, отдельно учитывать неизвестный результат
и сверять его с брокером; неизвестность нельзя превращать в разрешение повторной
отправки. Конкретные идентификаторы и правила такой сверки определяются
спецификацией брокерского протокола, а не выбором SQLite.

## Устойчивость, версия и границы диска

SQLite документирует WAL + FULL как ACID: FULL добавляет синхронизацию WAL
после каждой фиксации. NORMAL сохраняет согласованность при штатных предпосылках,
но допускает потерю подтверждённых транзакций при сбое ОС или питания; EXTRA
в WAL не усиливает FULL. Для финансового журнала рекомендуем FULL и проверку
фактического режима на каждом соединении, способном писать, включая служебные.
Настройку нельзя считать применённой только по успешному вызову: неизвестные
PRAGMA SQLite игнорирует. [SQLite: synchronous и правила PRAGMA](https://www.sqlite.org/pragma.html#pragma_synchronous).

Гарантия ограничена корректностью всей цепочки VFS, ОС, файловой системы,
виртуального диска, контроллера и носителя. SQLite полагается на завершение
синхронизации; ложное подтверждение хранилища может лишить commit устойчивости,
а сбой синхронизации при checkpoint — повредить базу. FULL не исправляет
неисправный диск. Поэтому подтверждённый commit и сохранность после реального
обесточивания — разные уровни доказательства.
[SQLite: Failure to sync](https://www.sqlite.org/howtocorrupt.html#failure_to_sync).

Версию библиотеки следует закрепить и проверять **внутри приложения**, отдельно
от версии Python, системной утилиты и Docker-образа. В марте 2026 исправлен
WAL-reset bug при конкурирующих записях/checkpoint из нескольких соединений:
исправление есть в SQLite 3.51.3 и новее, также заявлены backport 3.44.6 и
3.50.7. Это минимальное конкретное ограничение исследования, не обещание
отсутствия иных ошибок в любой более новой сборке.
[SQLite: WAL-reset bug, раздел 11](https://www.sqlite.org/wal.html),
[SQLite: release 3.51.3](https://www.sqlite.org/releaselog/3_51_3.html).

## Один writer и постоянное хранилище

SQLite разрешает несколько читателей, но лишь одну одновременную пишущую
транзакцию. Конкуренция может завершиться SQLITE_BUSY; ошибки I/O, заполнение
диска и нехватка памяти могут откатить отдельный оператор либо всю транзакцию.
Проектная рекомендация: короткие транзакции, ограниченное ожидание блокировки,
явная обработка результата и остановка новых торговых действий при невозможности
достоверно сохранить журнал. Сетевой вызов брокеру не должен удерживать
транзакцию. [SQLite: Transaction](https://www.sqlite.org/lang_transaction.html).

WAL позволяет чтение одновременно с записью; долгий читатель может задержать
checkpoint и увеличивать WAL. Все пользователи одного WAL должны находиться
на одном хосте, сетевые файловые системы не поддерживаются. Рекомендуем
наблюдать размер WAL, свободное место и завершение checkpoint, а не удалять
WAL вручную. Критически связанные изменения следует помещать в одну базу:
WAL не даёт общей атомарности нескольким присоединённым базам.
[SQLite: WAL](https://www.sqlite.org/wal.html).

Для проекта предпочтителен именованный Docker volume на **локальной Linux ФС**,
с целым каталогом базы и служебных файлов. Docker хранит volume вне жизненного
цикла контейнера; при этом его можно удалить, и один volume может быть подключён
к нескольким контейнерам. Более того, именованные volumes допускают NFS/CIFS:
само имя и даже название драйвера не доказывают локальность. Проверять нужно
реальную конфигурацию и backing storage. Volume не является резервной копией.
[Docker: volumes](https://docs.docker.com/engine/storage/volumes/).

Локальный Linux bind mount не запрещён SQLite сам по себе. Предпочтение volume —
проектное упрощение управления. Для Docker Desktop на Windows нельзя переносить
выводы о native Linux без проверки слоёв VM/WSL. Docker рекомендует Linux ФС
вместо Windows-пути для bind mounts по производительности; эта рекомендация
**не доказывает** повреждение SQLite на каждом Windows bind mount, но и не
подтверждает требуемую устойчивость. Рабочую базу предлагается не размещать
на Windows/network bind mount в первоначальном поддерживаемом профиле.
[Docker: WSL best practices](https://docs.docker.com/desktop/features/wsl/best-practices/).

## Резервная копия и восстановление

Предпочтительный механизм — SQLite Online Backup API в отдельную базу назначения.
Он создаёт согласованную копию работающей базы и допускает порционное копирование.
Произвольное архивирование live-volume средствами Docker этого свойства
не добавляет. [SQLite: Backup API](https://www.sqlite.org/backup.html).

Успех необходимо определять по полному завершению копирования и проверке ошибок,
а не по наличию файла: освобождение backup-объекта само по себе не подтверждает
полноту. Изменения источника между шагами могут перезапускать копирование,
поэтому начало backup нельзя безусловно объявлять точным временем снимка.
Проектная рекомендация: сохранять завершённую копию с идентификатором,
временем завершения, версией схемы/приложения и границей записей самого снимка;
затем проверять и переносить на независимый носитель.
[SQLite: контракт Online Backup API](https://www.sqlite.org/c3ref/backup_finish.html).

Один файл db может не содержать уже подтверждённые изменения из WAL.
Последовательное копирование db и WAL во время записи тоже не гарантирует
согласованности. Файловое копирование допустимо только при обеспеченной
неизменности источника; после аварии нужны относящиеся к нему журналы.
Нельзя смешивать базу и WAL разных состояний или удалять аварийный WAL ради
«чистого запуска». Для штатных копий выбираем Backup API.
[SQLite: backup/restore и журналы](https://www.sqlite.org/howtocorrupt.html#backup_or_restore_while_a_transaction_is_active).

Предлагаемый порядок восстановления:

1. Запретить отправку заявок и остановить экземпляры, использующие старую базу.
   Сохранить исходные файлы для разбора; не перезаписывать единственный оригинал.
2. Восстанавливать проверенную копию в отдельное чистое место, без старого WAL;
   проверить версии, целостность и доменные инварианты.
3. Сверить записи, неизвестные результаты, заявки и исполненные сделки с брокером
   за промежуток после снимка; восстановить остаток повторения. Структурно
   исправная копия может быть устаревшей и не содержать реальную сделку.
4. Представить результат сверки владельцу. Возобновлять торговые действия
   **только по его команде после сверки**. Торговую историю автоматически
   не удалять. Это согласованное требование пользователя, а не действие,
   выполненное в рамках исследования.

Полная integrity_check и отдельная foreign_key_check полезны для технической
проверки; первая не проверяет внешние ключи. Они не доказывают полноту
брокерской истории или правильность расчёта остатка повторения.
[SQLite: integrity_check](https://www.sqlite.org/pragma.html#pragma_integrity_check).

## Миграции, перенос и вторая копия

Рекомендуемый протокол миграции: запрет торговли, завершённая резервная копия,
проверка ожидаемой версии схемы, единственный владелец миграции, транзакционное
изменение с проверкой ограничений, затем проверка совместимости приложения.
SQLite документирует перенос содержимого и восстановление зависимых индексов,
представлений и триггеров для сложных изменений схемы. Неизвестная версия
должна останавливать запуск, а не запускать неявное исправление.
[SQLite: Making Other Kinds Of Table Schema Changes](https://www.sqlite.org/lang_altertable.html#otheralter).

Перенос на сервер предлагается проводить как управляемое восстановление:
сначала остановка отправителя на ПК и исключение его автозапуска, затем
копия, проверка и сверка на сервере. Если прежний хост недоступен и его
отключение нельзя подтвердить, новую отправку не разрешать до отдельного
решения об исключении старого отправителя. Смена адреса базы этого не решает.

**Вывод из области действия файловых блокировок:** две независимо скопированные
базы имеют независимые блокировки. Одинаковые UUID, записи «владелец» или lease
внутри каждой копии не обеспечивают единственность отправителя. Локальная защита
второго процесса полезна только для общего локального ресурса; блокировка
записи SQLite не равна блокировке всей жизни программы и её запросов брокеру.
Это ограничение протокола, не дефект WAL.
[SQLite: File locking problems](https://www.sqlite.org/howtocorrupt.html#file_locking_problems).

PostgreSQL стоит пересмотреть при потребности в общей серверной базе для
нескольких процессов, большей конкуренции записи или штатном PITR. Он предлагает
разные уровни блокировок и непрерывное архивирование, но требует отдельного
сервиса и его эксплуатации. Advisory lock имеет прикладной смысл и требует
правильного использования; **он не блокирует брокеру запрос старого процесса**
после потери связи с БД. Lease также не становится внешним fencing без
проверки права отправки принимающей стороной. PostgreSQL сохраняет зависимость
от надёжности дисковых кэшей. Для одного хоста это не обязательная замена SQLite.
[PostgreSQL: locking](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS),
[backup](https://www.postgresql.org/docs/18/backup.html),
[reliability](https://www.postgresql.org/docs/18/wal-reliability.html).

## Что ещё не подтверждено

До эксплуатационной приёмки остаются: фактическая runtime-версия SQLite,
режимы всех соединений, тип volume/ФС и цепочка синхронизации; результаты
аварийного завершения и отключения питания на целевом стенде; поведение
при заполнении диска и блокировке; восстановление реальной копии без повторной
отправки; исключение второго экземпляра при переносе. Не выбраны периодичность
копий, допустимая потеря локальных данных и срок восстановления.

Эти условия требуют отдельного плана и разрешённых испытаний. Закрытие
исследовательского билета означает наличие документированного основания
для спецификации, а не пройденную живую приёмку.
