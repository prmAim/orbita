# T-Invest API: доступ к исполнениям счёта автоследования

Дата документального исследования: 2026-11-08.
Билет: [Проверить доступ API к исполнениям счёта автоследования и операциям счёта повторения](https://github.com/prmAim/orbita/issues/2).
Карта: [Wayfinder: независимое пропорциональное повторение сделок](https://github.com/prmAim/orbita/issues/1).

## Вывод и границы доказательств

Официальная документация описывает необходимые общие механизмы: чтение счетов, истории и исполнений, состояние портфеля, выставление и сверку заявок. **Доступ этих механизмов именно к подключённому счёту подписчика автоследования не установлен.** Не установлена и невозможность такого доступа. Общая поддержка брокерских счетов не снимает этот вопрос.

Отдельный Autofollow API адресован другой роли. Точная короткая цитата официального описания: «Сервис автоследования предназначен для авторов стратегий». Его сигналы и портфель стратегии не являются подтверждением получения фактических исполнений собственного счёта подписчика. [Описание Autofollow API](https://developer.tbank.ru/invest/services/autofollow/head-autofollow), [каталог API для авторов](https://developer.tbank.ru/invest/api/autofollow).

Это исследование публичных документов, не живая приёмка. Личные счета, токены, `.env`, торговые методы и туннель не использовались. Прочитаны официальные страницы через поисковый индекс; часть прямых открытий портала завершалась timeout. Ни отсутствие явной гарантии в найденных документах, ни такой timeout не доказывают запрет API.

## Подтверждено / не установлено / нужна живая проверка

| Область | Подтверждено документацией | Не установлено | Нужна живая проверка |
| --- | --- | --- | --- |
| Счёт источника | Есть общие методы счетов и отдельный авторский Autofollow API | Гарантия видимости счёта подписчика и всех его исполнений | GetAccounts, история известной сделки, подписки и естественное исполнение |
| История | GetOperationsByCursor, пагинация; ID операций могут меняться | Неограниченное полное восстановление и постоянный общий ключ между источниками | Повторная выгрузка, сопоставление со стримом и отчётом |
| Частичное исполнение | Есть сделки и показатели исполненного количества | Полнота полей для автоследования, точная задержка доставки | Естественная частичная сделка; если не встретилась — сценарий непроверен |
| Капитал | Есть стоимость портфеля, позиции и денежные остатки | Равенство одного поля принятому в проекте капиталу во всех классах активов | Сверка состава, валют, блокировок и времени снимков |
| Счёт повторения | Общий API отправки и сверки заявок существует | Фактические торговые права именно этого счёта | Чтение прав и доступности инструментов; исполнение отдельным будущим этапом |
| Сбои отправки | Ключ идемпотентности и запрос по его типу | Безусловная гарантия отсутствия дублей при любых сроках и сбоях | В этом read-only этапе не проверяется |
| Sandbox | Виртуальные счета и упрощённое исполнение | Эквивалентность реальному счёту автоследования | Sandbox не закрывает проверку источника |

Источники и условия для строк таблицы приведены ниже. «Нужна живая проверка» означает план, а не разрешение на её запуск.

## Счета и права

`GetAccounts` возвращает идентификатор, тип, статус и уровень доступа. В перечислении типов есть брокерский счёт и ИИС, но отдельного типа «счёт подписчика автоследования» нет. Следовательно, одного `type` недостаточно, чтобы идентифицировать источник; владелец должен сопоставить `account_id` с нужным счётом. [Контракт счетов](https://developer.tbank.ru/invest/services/accounts/users).

Поддержка нескольких счетов документирована; операции, портфели и лимиты учитываются раздельно. Это подтверждает модель двух счетов, но не специальную доступность подключённого счёта. [Общий FAQ](https://developer.tbank.ru/invest/intro/faq).

Read-only token предназначен для чтения и не позволяет выставлять поручения. Есть токены отдельного счёта с настраиваемыми правами; `full-access` допускает торговые методы. Для некоторых специальных продуктов документация требует токен всех счетов, но не даёт отдельного правила для счёта подписчика автоследования. Поэтому предложение для проверки — минимальные права чтения; возможность ограничить токен источником необходимо установить, а расширять права автоматически нельзя. [Токены](https://developer.tbank.ru/invest/intro/intro/token).

## История, стримы и идентичность исполнения

Банк рекомендует `GetOperationsByCursor`: он поддерживает пагинацию и отменённые операции. Старый `GetOperations` ограничен последней тысячей записей. Операции могут появляться позже исполнения, поэтому банк не рекомендует их как оперативный индикатор статуса заявки. [Описание сервиса операций](https://developer.tbank.ru/invest/services/operations/head-operations).

В текущем контракте истории есть `quantity_done`, `quantity_rest`, сделки и признак следующей страницы; максимальный `limit` — 1000. Статус `OPERATION_STATE_EXECUTED` означает как полное, так и частичное исполнение. В типах операций предусмотрены комиссии автоследования; это признак моделирования таких событий, но не гарантия доступности конкретного счёта. [Контракт операций](https://developer.tbank.ru/invest/services/operations/methods).

Критические оговорки банка из [особенностей операций](https://developer.tbank.ru/invest/services/operations/operations_problems):

- Точная цитата: «ID операций могут меняться со временем». Применять их как постоянный первичный ключ нельзя.
- `trade_id` истории иногда отличается от идентификатора сделки в сервисе заявок. Рекомендованный банком путь — получить ID операции и запросить `GetOrderState`, передав этот ID как `order_id`.
- После корпоративных действий история может оказаться неполной; для точной сверки банк указывает брокерский отчёт.
- Для курсорной пагинации рекомендуется `limit > 2`.

`TradesStream` предназначен для событий фактического исполнения поручений. [Описание сервиса заявок](https://developer.tbank.ru/invest/services/orders/head-orders). Его сделка содержит `trade_id`, время, цену и количество **штук**; `OrderStage.quantity` в ответе состояния заявки описан в **лотах**. Это разные единицы одного семейства API. `OrderStateStream` содержит исполненные/оставшиеся лоты и идентификаторы заявки/запроса. [Контракт заявок](https://developer.tbank.ru/invest/services/orders/methods).

Однако статья о `OrderStateStream` предупреждает: первое событие может содержать внутренний, а не биржевой `order_id`; после частичного исполнения отменённая заявка в стриме сохраняет частичный статус; список сделок может быть опциональным. Поэтому одно событие статуса нельзя считать ни гарантией полного исполнения, ни полным реестром сделок. [Особенности стрима заявок](https://developer.tbank.ru/invest/services/orders/orders_state_stream).

Для WebSocket лента сделок помечена устаревшей, рекомендован стрим заявок; это отдельная оговорка протокола, а не основание объявлять весь gRPC TradesStream удалённым. [WebSocket](https://developer.tbank.ru/invest/intro/developer/protocols/ws).

**Инженерный вывод для будущей спецификации:** после разрыва нужен перекрывающийся повторный запрос истории с повторной сверкой, а не доверие только последнему cursor или ID операции. Кандидат ключа исполнения — счёт + идентификаторы сервиса заявок + trade_id; его стабильность и соответствие истории нужно проверить. В изученных источниках не найдена гарантия replay пропущенных событий, exactly-once доставки или неограниченного хранения доступных состояний заявок. До установления правил конфликтов неоднозначные записи должны останавливать автоматическое повторение.

## Капитал и единицы

`GetPortfolio` предоставляет `total_amount_portfolio`, оценки по классам активов и валютам; `GetPositions` — деньги, блокировки и позиции. Есть `limits_loading_in_progress`. Эти поля дают исходные данные, но документация не доказывает, что одна сумма точно совпадает с определением проекта «активы плюс свободные деньги». [Контракт операций](https://developer.tbank.ru/invest/services/operations/methods).

Оценка портфеля использует текущие цены, а вне торгов — последние цены закрытия. [Описание операций](https://developer.tbank.ru/invest/services/operations/head-operations). **Вывод:** нельзя добавлять свободные деньги к общей сумме без проверки состава — возможен двойной счёт. Нужно согласовать валюту оценки, момент снимка, блокировки, долг, производные и НКД. Свободные средства для новой заявки и капитал для пропорции — разные величины. Атомарность снимков двух счетов документацией здесь не установлена.

`PostOrder.quantity` — целое количество лотов, цена задаётся за единицу инструмента; для облигаций/фьючерсов важен `price_type`. [Контракт заявок](https://developer.tbank.ru/invest/services/orders/methods). Метаданные инструмента дают `lot`, `min_price_increment`, доступность покупки/продажи и `api_trade_available_flag`; есть требования к тестам клиента. [Контракт инструментов](https://developer.tbank.ru/invest/services/instruments/methods).

**Вывод:** пропорциональный объём не гарантированно кратен лоту. Правила округления, накопления остатка и предельной цены ещё требуют решения пользователя; нельзя молча копировать число лотов или применять одну формулу цены к любому классу активов.

## Идемпотентность и неизвестный результат

FAQ различает входной `order_id` как ключ идемпотентности и выходной биржевой `order_id`. Дедупликация определяется парой ключ + счёт. Повторный `PostOrder` с той же парой должен возвращать состояние ранее выставленного поручения. Точная цитата (грамматика источника сохранена): «Ключ хранится один месяц, но пока мы не может дать гарантию его сохранности». Там же для получения завершённых заявок через `GetOrders` указаны ограничения: только текущий день, до 100 записей, окно запроса до часа. [FAQ заявок](https://developer.tbank.ru/invest/services/orders/faq_orders).

`GetOrderState` принимает `order_id_type=ORDER_ID_TYPE_REQUEST`, позволяя читать состояние по клиентскому ключу. [Контракт заявок](https://developer.tbank.ru/invest/services/orders/methods). Каталог ошибок предусматривает даже дубликат без найденного отчёта (`30057`). [Ошибки API](https://developer.tbank.ru/invest/intro/developer/error-codes/errors).

**Предложение для спецификации, не выполненная торговая проверка:** сохранить намерение и уникальный ключ до отправки. Timeout считать неизвестным результатом; сначала читать состояние по тому же ключу, затем сверять заявки и операции. Не создавать новый ключ лишь из-за сетевой ошибки. Неразрешённый результат блокирует повторную отправку до сверки. Безусловное exactly-once между программой и брокером исследованием не доказано.

## Лимиты и sandbox

Опубликованы лимиты на пользователя, распространяющиеся на все его счета: операции — 200 запросов/мин, счета — 100, `PostOrder` — 15/сек, `GetOrders` — 200/мин; для стримов ордеров — 16 на тип, операций — 11 на тип. Это текущие документальные значения, а не результат измерения персональной квоты. [Лимиты](https://developer.tbank.ru/invest/intro/intro/limits).

Песочница использует виртуальные счета, не связанные с реальными торгами. Рыночная заявка исполняется по последней цене независимо от глубины, лимитная может исполниться целиком при встречном предложении всего на один лот. Нет обычного расчёта налогов, купонов и дивидендов; комиссия фиксирована, показатели риска упрощены, брокерский отчёт пустой. Поэтому sandbox полезен для проверки форматов и локальной логики, но не подтверждает доступ подписчика, реальные частичные исполнения, проскальзывание или пригодность расчёта капитала. [Песочница](https://developer.tbank.ru/invest/intro/developer/sandbox).

## Минимальный план будущей проверки только чтением

План требует отдельного запуска владельцем или его явной авторизации. Секрет остаётся локально у владельца; в чат, GitHub и отчёт не передаются токен, номера счетов и сырые персональные ответы. Предлагаемые шаги:

1. Владелец подтверждает, какой счёт подключён к автоследованию, и выбирает уже состоявшуюся известную сделку для сравнения. Используется read-only токен минимально доступного охвата; никакие настройки торговли не меняются.
2. Вызвать `GetAccounts`, сопоставить оба счёта, зафиксировать обезличенно тип, статус и права. Отсутствующий источник означает неуспех этой проверки; причина (охват токена, тип продукта, ограничение банка) выясняется отдельно, без автоматического расширения прав.
3. Для источника прочитать `GetOperationsByCursor` за небольшой интервал вокруг известной сделки, пройти все страницы с `limit=100` и включёнными сделками. Сверить направление, инструмент, количество, время и цену с данными владельца. Проверить `GetOrderState` для ID операции по рекомендованному банком пути. Через некоторое время повторить чтение и записать, менялись ли идентификаторы/состав.
4. На обоих счетах прочитать `GetPortfolio` и `GetPositions` максимально близко по времени, в согласованной валюте; сверить активы, деньги и блокировки. Неполную выгрузку лимитов или несогласованные снимки пометить непригодными для расчёта.
5. Проверить подтверждение подписки на `OrderStateStream` и выбранный поддерживаемый стрим исполнений источника. Дождаться естественного события автоследования, не создавая сделку ради теста. Сравнить событие с последующей историей и состоянием заявки. Если события не было, результат — только «подписка принята», а не «исполнения доступны».
6. Переподключить только клиентский стрим, не меняя сеть/туннель; восстановить перекрывающийся интервал истории. Сопоставить исполнения до/после, проверить отсутствие повторного учёта. Частичное исполнение и событие во время разрыва признаются проверенными только если реально наблюдались.
7. На счёте повторения ограничиться чтением заявок, прав и метаданных тех же инструментов. Успех чтения не объявлять подтверждением возможности выставления. Сохранить локальный обезличенный протокол: время, методы, коды ошибок, количество страниц/событий, результат сопоставления и явные непроверенные сценарии.

Критерий снятия основного барьера: доказано соответствие конкретного подключённого счёта, прочитано известное исполнение, получено естественное событие и показана его сверка после переподключения. Если хотя бы одна часть отсутствует, формулировать более узкий результат. При отказе доступа следующий шаг — вопрос поддержке банка о **чтении счёта подписчика при активном автоследовании**, без секретов и без обращения к API автора стратегии как замены.

## Состояние исследования

Документальное исследование завершено; пригодность живого доступа и торговая приёмка остаются неустановленными. Код приложения не изменён. Дальнейшие решения: разрешить ли отдельную read-only проверку, выбрать правила расчёта капитала/округления и определить поведение при неоднозначной истории либо неизвестном результате отправки.
