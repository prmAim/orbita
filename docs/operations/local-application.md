# Локальное приложение Orbita

Первая версия работает на ПК в Docker. Запуск не подтверждает живую торговую
приёмку. До заполнения подтверждённых параметров счетов, времени, капитала,
ресурсов и комиссии торговые действия остаются заблокированы.

Подключение настоящего SDK, файл токена, частное монтирование и проверяемый
профиль счетов описаны в [квалификации брокера](broker-qualification.md).
Независимые подтверждения [времени](qualified-clock-evidence.md) и
[стоимости в RUB](qualified-rub-valuation.md) имеют отдельные протоколы и сроки.

## Сборка и запуск

Нужны Docker Desktop с Linux containers и доступ к опубликованным образам и
Maven/npm во время первой сборки. Для разработки используются Java 25 и Node.js.

1. Скопировать `deploy/.env.example` в локальный `deploy/.env` и задать разные
   случайные пароли приложения и bootstrap-администратора БД. Администраторский
   пароль получает только контейнер PostgreSQL. Файл исключён из Git. Не
   передавать его содержимое в чат.
2. Создать выбранную папку на USB и сохранить её абсолютный путь в
   `ORBITA_USB_DIRECTORY`. Монтирование не создаёт отсутствующую папку.
3. Выполнить `powershell -File deploy/start.ps1 -Build`. Команда создаёт отдельный
   compose-проект `orbita`, его сеть и два тома; существующие проекты не меняет.
4. Выполнить `powershell -File deploy/reset-password.ps1` в интерактивном
   терминале и ввести новый локальный пароль дважды. Пароль не попадает в
   аргументы процесса или переменные среды. Минимум 12 символов, максимум
   72 байта UTF-8. Отмена после начала сброса оставляет доступ закрытым.
5. Открыть `http://127.0.0.1:8086`. PostgreSQL не публикует порт на хосте.

`deploy/install-autostart.ps1` — отдельная, явно запускаемая владельцем установка
задачи Windows после входа в систему. Скрипт не открывает браузер. Перед запуском
проверить доступность Docker Desktop после входа. Установка автозапуска не
выполняется при сборке или тестах.

Последующие запуски `start.ps1` используют уже собранный образ и не требуют
пересборки или скачивания зависимостей. После изменения исходников нужен `-Build`.

Приложение возвращает фактический режим, а не трактует успешный HTTP-ответ как
разрешение торговать. Разовый допуск требует каждый раз нового предела RUB.
Остановка и отзыв допуска — разные команды. Выход закрывает доступ к панели и
сохраняет режим повторения. Правила сеанса описаны в ADR 0001.

## Журнал и уведомления

Текст уведомления, московское время и UUID хранятся в основной PostgreSQL и
показываются в панели без переформулирования. Сетевой вызов Telegram выполняется
после транзакции, отдельным исполнителем. PostgreSQL queue claim использует
`FOR UPDATE SKIP LOCKED` через JDBC на том же DataSource и в той же Spring/JPA
транзакции, что и доменное изменение. Вызов `NotificationPublisher` вне
транзакции запрещён. Повтор не меняет UUID. Успех прекращает повторы; история
попыток автоматически не удаляется. Telegram не принимает торговых команд.

Для каждой новой попытки отдельно сохраняется неизменяемый текст фактически
начатой отправки. Если блокировка снялась во время ожидания успешного ответа,
журнал первоначального уведомления сохраняет отправленный текст, а снятие
получает одно отдельное уведомление. При ошибке или неизвестном результате
повтор сохраняет первоначальный ID и содержит оба события. Для старых попыток,
созданных до записи payload, отсутствие текста отмечается явно; исторические
доказательства не достраиваются предположениями.

Telegram по умолчанию выключен. При включении разрешён один положительный
числовой ID личного чата; групповые ID отклоняются. Токен и ID задаются только
локальной конфигурацией. Десять секунд включают соединение и ответ. Неизвестный
результат не повышает счётчик подтверждённых автоматических неудач.

## Временные демонстрационные данные

Демонстрационные сделки должны проходить полный интеграционный сценарий:
официальный SDK обращается к локальному TLS-симулятору, а приложение принимает
исполнения, рассчитывает повторение и формирует журнал и очередь уведомлений.
Прямая загрузка торговых примеров SQL-вставками не используется. Это временные
данные для просмотра интерфейса, не доказательство живой торговой приёмки.

Набор содержит 15 бумаг с меткой `[ТЕСТ]`; у пяти есть повторные покупки и
продажи. Отдельные сценарии включают частичные исполнения, отмены и пропуски.
Ожидаемые остатки перечислены
в [матрице предпросмотра](../acceptance/interface-preview.md). Все инструменты
доступны в «Активах», активные заявки — в «Инструментах», история — в
«Операциях». Компактное управление паузами остаётся в разделе «Управление»,
включая инструменты без текущего остатка. Более ранние решения доступны в журнале.

Сначала сохранить отдельный локальный Compose override и запускать предпросмотр
с ним. В `services.app.environment` должны быть явно заданы строки:

```yaml
ORBITA_BROKER_ENABLED: "false"
ORBITA_TELEGRAM_ENABLED: "false"
ORBITA_WORKER_ENABLED: "false"
ORBITA_BACKUP_ENABLED: "false"
```

Счета и параметры токенов должны оставаться пустыми. После изменения override
пересоздать приложение через `deploy/start.ps1 -ComposeOverride <путь>`.
Затем выполнить из корня репозитория, подставив свой постоянный локальный файл:

```powershell
./deploy/demo-data.ps1 -Action Generate -Project orbita -ComposeOverride <путь> -ValidateOnly
./deploy/demo-data.ps1 -Action Generate -Project orbita -ComposeOverride <путь> -OwnerPasswordFile <приватный-файл>
./deploy/demo-data.ps1 -Action Remove -Project orbita -ComposeOverride <путь>
```

`-EnvironmentFile` позволяет явно выбрать существующий локальный файл настроек.
`-Scenario Standard` используется по умолчанию и сохраняет прежнюю команду.
`Large` добавляет более 100 исторических внешних заявок через SDK-имитатор
для проверки глобальных фильтров, сортировки и страниц 25/50/100; торговые факты
по-прежнему создаются только приложением. Между наборами сначала выполнить Remove.
Для большого набора после удаления предыдущего:

```powershell
./deploy/demo-data.ps1 -Action Generate -Scenario Large -Project orbita -ComposeOverride <путь> -OwnerPasswordFile <приватный-файл>
```

**Переход со старого предпросмотра:** манифест версии1 нужно удалить командой
Remove на схеме15 **до обновления образа приложения и миграции БД**. Затем
обновить приложение до схемы17 и выполнить Generate. Новый Generate требует
схему17 и создаёт манифест версии2. Remove понимает пары: версия1/схема15
и версия2/схема16–17; несовместимая пара отклоняется без изменений. Если старый
манифест уже перенесён на новую схему, не удалять реестр вручную: восстановить
проверенную копию с прежней версией и удалить старый набор штатно.

`Generate` запускает тот же `InterfaceDemoIT`, который обычно работает с отдельным
PostgreSQL Testcontainer, и сохраняет результаты полного сценария в выбранной БД.
На время проверки останавливается именно проверенный контейнер интерфейса,
БД получает случайный порт только на `127.0.0.1`. Пароль БД передаётся тесту
через среду дочернего процесса. Существующий пароль владельца читается самим
тестом из приватного файла для обычного входа через HTTP; сброса пароля нет.
После теста временная публикация БД снимается и запускается тот же контейнер
интерфейса. Отчёты Maven остаются в игнорируемом `.scratch/interface-preview/runs/`.
Нужна Java 25; `-JavaHome` и `-MavenRepository` позволяют явно выбрать установленную
JDK и существующий локальный Maven cache. Сценарий обращается только к локальным
имитаторам брокера и доставки, без настоящих заявок и Telegram-сообщений.

Генерация требует режима `NOT_STARTED`, отсутствия торговых фактов, допусков,
квалификации и готовой к доставке старой очереди. Обычный журнал, уже доставленные
уведомления, пароль и существующие копии не заменяются. Повторный `Generate`
отклоняется до удаления предыдущего набора и сохраняет внесённые через интерфейс
изменения. Отдельный реестр хранит исходные ключи и точные ID созданных сценарием
записей; исходное состояние управления восстанавливается после остановки теста.
Для таблиц чтения используются точные JSON-ключи из account/kind/id,
account/section и account. Прежние строки, включая созданную офлайн-чтением
`unconfigured` revision, не присваиваются набору. Захват владения выполняется
после закрытия lifecycle, SDK-потоков, контекстов и соединений теста.
Поздняя пауза или повтор уведомления может создать производные строки: Remove
удаляет их только в уже подтверждённой области счёта и инструментов набора.
Новые или изменившиеся банковские наблюдения в этой области делают происхождение
неоднозначным и останавливают удаление. Данные счёта целиком не удаляются.

Проверяются и итоговая Compose-конфигурация, и фактически работающий контейнер;
неподходящий профиль отклоняется до обращения к данным. Удаление затрагивает
только демонстрационные записи из их отдельного реестра. После удаления тот же
override остаётся выключенным: скрипт не включает брокера, Telegram, исполнители
или резервное копирование. Для последующих запусков предпросмотра сохранять
этот override; переход к рабочему профилю выполнять отдельно после удаления данных.
При аварийном завершении процесса восстановить исходный профиль той же командой
`deploy/start.ps1 -ComposeOverride <путь>` и проверить отсутствие опубликованного
порта БД до повторного запуска. Не считать частичный отчёт успешной проверкой.

## Резервные копии

Расписание — первое число месяца, 03:00 МСК; проверка срока происходит каждую
минуту, в том числе после сна. Пропущенный срок создаёт одну текущую месячную
версию. Неудача создания повторяется через час; перенос проверенной версии
повторяется независимо через час. Хранятся текущий и два предыдущих календарных
месяца; пропуск месяца не продлевает хранение старой версии.

Экспорт использует `pg_export_snapshot` и `pg_dump --snapshot`, поэтому копия и
контрольные количества таблиц относятся к одной границе. Архив действительно
восстанавливается через `pg_restore --exit-on-error` в отдельную временную БД.
Сравниваются состав таблиц, количества строк, SHA-256 упорядоченного содержимого
каждой таблицы и целостность ссылок уведомлений.
После проверки архив атомарно переименовывается и получает SHA-256. USB-перенос
проверяет SHA-256 до и после копирования и использует временный файл. Создание
архива не блокирует торговую транзакцию на время сетевых или файловых операций.

Приложению доступны PostgreSQL client tools из того же образа 17.11, что и БД.
Bootstrap-администратор `orbita_admin` отделён от приложения. Роль `orbita` не
является superuser и не создаёт роли; CREATEDB нужен
для изолированной проверки восстановления. Временная проверочная БД получает
случайное имя `orbita_verify_*`; рабочая БД не является целью `pg_restore`.

Проверка содержимого устанавливает воспроизводимость границы и работу
ограничений PostgreSQL; она не заменяет сверку торгового результата с брокером.

После восстановления снимка месячная запись может ещё содержать `CREATING`,
хотя проверенный архив того же месяца уже находится на USB или ПК. Если такая
версия или её USB-файл SHA-256 существует, приложение не создаёт новую копию и
не перезаписывает старую. Панель показывает «Месячная копия уже существует,
нужна ручная сверка». До сверки нельзя считать восстановленную запись `CREATING`
доказательством отсутствия архива.

Ручная сверка: сохранить существующие архив и SHA-256; сравнить хеш, затем
восстановить именно этот архив в новый изолированный проект по процедуре ниже.
Сверить журнал, пару счетов и протокол исторического расчёта. Не удалять единственный
архив и не снимать блокировку правкой статуса ради запуска нового `pg_dump`.
Автоматическое принятие найденного файла как копии текущей БД не выполняется:
выбранная папка может содержать архив другой базы. Текущая месячная версия
остаётся под ручной сверкой; следующий месячный срок создаёт новую версию в обычном
порядке. Эта блокировка касается создания данной месячной версии, торговое
состояние и другие проверенные копии она не меняет.

## Восстановление

Выбрать последний проверенный `orbita-YYYY-MM.dump` и его `.sha256` на USB.
При потере диска допустима более старая последняя доступная копия по R120.
Выполнить `powershell -File deploy/restore.ps1 -Backup E:/OrbitaBackups/orbita-2026-11.dump`.
Скрипт требует новое имя проекта `orbita-restored-*` и отдельный HTTP-порт,
проверяет SHA-256 и восстанавливает новую БД. Работающее приложение исходного
проекта не останавливается и не меняется.

Для изолированного стенда скрипты `start.ps1`, `reset-password.ps1` и `restore.ps1`
принимают `-EnvironmentFile` и `-ComposeOverride` с существующими файлами.
Стенд может заменить `/usb` отдельным именованным томом; это файловый имитатор,
который не подтверждает доступность или сохранность физической USB-флешки.

До запуска восстановленного приложения устанавливаются режим RESTORED,
непройденная сверка и отключённая готовность потока; разрешение и автоматическая
отправка отменяются. Прежняя очередь уведомлений игнорируется, локальный пароль
сбрасывается. Затем требуется новый пароль, свежие оценки обоих счетов и сверка.
«Начать» заново получает оценки и приводит к теневому расчёту. Автоматическую
отправку владелец включает отдельно после необходимых условий.

R121 измеряется от начала `restore.ps1` до подтверждённой готовности приложения
к сверке в режиме чтения. Время самой сверки не входит. Скрипт выводит начало;
конечную точку нужно сохранить по фактическому состоянию приложения. Успешный
возврат Docker Compose сам по себе этой конечной точкой не считается.

## Проверки

### Сверка после переноса на сервер (R127)

Этот этап следует только после живой приёмки на ПК. В разделе «Копии» указать ID
проверенного исходного исполнения из протокола теневой сверки и сохранить JSON
«Протокол с ПК». Приложение повторно читает это исполнение из независимой истории
брокера и проверяет сохранённый расчёт. Файл содержит SHA-256 журнала до явной
границы ID, настройки пары счетов и ограничений в виде отпечатка, отпечатки
исполнения и расчёта, версию алгоритма и время. Пароли и токены в него не входят.

После переноса проверенной базы открыть панель на ПК владельца, загрузить тот же
JSON и нажать «Сверить после переноса». Сравниваются сохранённый префикс журнала,
настройки, вновь прочитанное исполнение и теневой расчёт с его первоначальным
коэффициентом. Новые записи о восстановлении после границы файла не влияют на
сравнение старого префикса. Если в нём изменился текст уведомления после снятия
блокировки, сравнение выявит отличие; сохранить согласованную проверенную копию
и новый протокол на ПК перед повторным переносом.

Каждый результат сохраняется в `migration_verification` и доступен панели.
Проверка не создаёт намерений, не отправляет и не отменяет заявки, не включает
автоматическую отправку и не снимает режим восстановленной копии. Изменение
runtime-режима, отзываемый допуск, сеансы и пароль намеренно не сравниваются как
настройки: после восстановления они подчиняются R43/R113–R126. Сравниваются
конфигурация пары, граница точности времени и подтверждение запрета маржи.
Совпадение хешей не заменяет независимого чтения истории: без него соответствующие
пункты остаются неподтверждёнными. Фактическая приёмка на постоянном сервере
выполняется отдельно после его выбора владельцем.

`npm ci --ignore-scripts`, `npm run typecheck`, `npm run build` в `frontend/`.
Скомпилированные статические файлы включаются в JAR; исходный интерфейс остаётся
единственным источником для изменений. `backend/mvnw verify` запускает модульные
и интеграционные тесты. Интеграционные тесты используют отдельные PostgreSQL
Testcontainers с динамическими портами и синтетические внешние данные.

Обычный запуск не выполняет живую приёмку, не устанавливает автозапуск Windows,
не меняет существующие контейнеры, сеть или туннель. Настоящие Telegram-сообщения,
USB, сон/перезагрузка Windows и брокерские эффекты проверяются отдельно по
матрице сценариев с разрешениями владельца.
